## 1. 产品定位与核心判断

**定位**：给冷备盘（写完即拔、存放到异地或柜中的硬盘）做"档案 + 核对"：采集全盘文件与目录清单形成快照，随时浏览查询，并与历史快照比对出新增、丢失、变化。**不负责也不执行任何数据同步。**

**核心判断**：v1 的问题不在采集逻辑，而在"用 CSV 当数据库"：三百万文件被写成 1.13GB 的动态列宽 tree.csv，无法查询、无法做目录级统计、比对每次全量重排。v0.3 的主线是：**每快照一个 SQLite 快照库 + 文件/目录统一条目模型 + 本地 Web 服务呈现**。

**典型使用场景**：

- **轮换核验**：盘在异地存放数月，接回后采集新快照，与手中旧快照 diff，确认内容与预期一致；
- **落盘盘点**：新盘写入前后各采一次，确认这次备份实际写入了什么、漏了什么；
- **找文件**：盘不在手边，仅凭快照回答"那份资料在哪块盘的哪个目录"；
- **空间分析**：哪个目录占了这 14TB、最大的文件有哪些、按扩展名分布如何；
- **健康档案**：每次采集记录 SMART（温度/通电小时/坏道计数），形成盘的简易健康趋势；
- **内容校验（按需）**：启用哈希后做全量或抽样内容校验，发现静默损坏、改名/移动与重复文件。

## 2. 现状与痛点（基于实测）

v1（`Legacy/backupStatus260505/backuptools/`，纯标准库、Windows PowerShell/WMI）现有能力：`collect` 产 metadata.csv / tree.csv / warnings.csv，`compare -d N` 产 diff.csv。实测样本：一块盘 2,981,921 个文件、52,536 个目录、约 1.87TB，tree.csv 达 1.13GB；另一块 SYNC 归档盘仅 22 个文件。

| 领域 | 现状 | 后果 |
|---|---|---|
| 存储 | 1.13GB CSV、动态 `level_1..N` 列 | 不可查询；快照间列宽漂移；27k+ 行带引号逗号，naive 解析会错列 |
| 数据模型 | 只有文件行；目录仅"空目录"一行；无哈希 | 无目录 mtime、无法算 du、目录增删不可见；内容变化不可检测 |
| 元数据 | model 记的是 USB 桥；无卷序列号/SMART/扩展名列；partition_style 恒空 | 认盘不可靠；空间与类型统计缺数据 |
| 采集 | 两遍 os.walk；per-file DictWriter；无续采；`--exclude-glob` 死代码 | 大盘耗时长；中断=重来；过滤不生效 |
| 比对 | 每次全量外排重算；仅比 type/size/mtime；无退出码 | 慢且只能回答有限问题；无法脚本化 |
| 数据质量 | warnings 每条重复 ×2；wmic 回退解析脆弱 | 需要人工清理；可靠性差 |
| 平台 | PowerShell/WMI/ctypes 锁死 Windows | 无法在 Linux 使用 |

## 3. 总体架构

### 3.1 组件与数据流

```
                        ┌──────────────── 主机 ────────────────┐
                        │                                      │
  浏览器 (SPA) ◄──HTTP/SSE──► 后端 API 服务 (FastAPI + uvicorn) │
                        │      │           │          │        │
                        │      ▼           ▼          ▼        │
                        │  catalog.db   快照库池    任务调度器  │
                        │  (注册+统计)  (只读 ATTACH) (采集/diff)│
                        │      │           │          │        │
                        └──────┼───────────┼──────────┼────────┘
                               │           │          │
        data/                  │           │          ▼
        ├─ catalog.db ◄────────┘           │     采集引擎 (单遍 scandir，
        ├─ <volume_id>/<ts>/snapshot.db ◄──┤     多分区批次，可续采)
        └─ _diffs/<diff_id>.db ◄───────────┘          │
                                                      │ 采集完成后自动拷贝
                        被采盘 (USB HDD)              ▼
                        E:\_coldmanifest\<volume_id>\<ts>\snapshot.db
```

| 组件 | 职责 | 形态 |
|---|---|---|
| 采集引擎 | 单遍 scandir 遍历、过滤剪枝、流式写 snapshot.db、scan_journal 续采、盘上备份 | 库代码，CLI 与 Web 任务共用同一入口 |
| 快照库 snapshot.db | 每卷每次采集一个不可变制品（entries / skipped / meta / dir_rollup） | SQLite，以 `mode=ro` 只读打开（不用 immutable=1，原因见 §5.1） |
| catalog.db | 注册表：盘 / 卷 / 快照 / 批次 / 盘上副本 / diff 记录 / 备注 + 预计算统计 | SQLite，WAL，可重建 |
| 后端 API | REST + SSE；读路径直开快照库；写路径仅 catalog 与任务 | FastAPI，单进程 |
| 前端 SPA | 数据呈现（表格 / 图表 / 目录树） | 构建产物由后端静态托管 |
| CLI `cldm` | serve / collect / import-legacy / import-db / diff / export / report / build-fts / build-stats / hash / duplicates / verify-copy / delete / nickname / integrity-check / identity-check / rebuild-catalog | argparse |

关键数据流：

1. **采集**（CLI 或 Web 发起）→ 任务调度器建批次 → 引擎逐卷产 snapshot.db 到 `data/<volume_id>/<ts>/` → 封库（建索引、dir_rollup、`PRAGMA optimize`）→ 自动拷贝到盘上 → catalog 登记快照与副本。
2. **浏览 / 查询**：API 按快照 ID 从 catalog 解析路径，以 `mode=ro` 只读连接直接查询对应 snapshot.db（LRU 连接池）。**不把 entries 导入统一资料库**。
3. **diff**：作为后台任务执行 SQL join（ATTACH 两库），结果物化到 `data/_diffs/<diff_id>.db`，API 分页查询物化结果。

### 3.2 数据面：快照库是唯一事实源

| 方式 | 结论 |
|---|---|
| **直读快照库（采用）** | 快照库即唯一事实源；catalog 只存注册信息与预计算统计；详情查询直开 / ATTACH 各库。≤20 快照规模下跨库操作只有 diff 与 history，ATTACH 完全够用，且保持"快照即可拷走制品"的性质 |
| 统一资料库（否决） | 把所有快照 entries 合并进一个大库。10–60M 行单库、写入路径复杂、快照失去自包含性、盘上备份不再是完整制品。当前规模不足以证明其必要性 |

### 3.3 技术栈

| 层 | 选型 | 理由 / 备选 |
|---|---|---|
| 后端 | Python 3.10+ / FastAPI + uvicorn | 与采集/diff 引擎同语言同进程，库代码直接复用；自带 Pydantic 校验与 OpenAPI 文档；SSE 用 StreamingResponse 即可。备选 Flask / Litestar 均可替换，但无必要 |
| 数据库 | Python 标准库 sqlite3 | 快照库 `mode=ro` 只读打开（不用 immutable=1）；catalog 用 WAL；不引入 ORM——本项目查询（前缀过滤、递归 CTE、跨库 join）正是 ORM 弱项，手写 SQL + 参数绑定 |
| 进度推送 | SSE | 进度是纯服务端→客户端单向流；基于普通 HTTP、自带断线重连；取消等双向操作用普通 POST，不构成引入 WebSocket 的理由 |
| 前端 | React 19 + TypeScript + Vite 8 + Ant Design 6 + ECharts | 数据密集型管理界面生态最厚；AntD Table 原生虚拟滚动、Tree 懒加载；ECharts 覆盖 treemap / 直方图 |
| 前端数据层 | TanStack Query + OpenAPI 生成 TS 客户端 | 服务端状态缓存、游标分页与失效管理 |
| 分发 | zip 包（Python 包 + 前端构建产物 + 启动脚本），解压后 `cldm serve` 运行；不要求单文件可执行程序 | uvicorn 单进程即可——瓶颈在磁盘 IO 与 SQLite，不在 WSGI 并发 |

### 3.4 部署形态

- 服务跑在**接盘的机器**上；Windows 与 Linux 同等支持。
- 默认绑定 `0.0.0.0:8765`，**局域网内可直接访问，不设鉴权**（信任内网环境）；只想本机使用时加 `--host 127.0.0.1`。
- **生产同源**：SPA 由 FastAPI 静态托管（history 路由 fallback 到 index.html），不开 CORS；开发期 vite dev server 代理 `/api`。
- **路径安全**：API 一律以 catalog 内 ID 寻址，不接受任意文件系统读路径。唯二例外：`/api/disks/attached`（枚举在线盘，输出平台层白名单字段）与导入接口（`path` 必须位于 settings 导入白名单根目录之下，解析符号链接后校验前缀，拒绝相对逃逸）。不存在"读任意文件内容"的端点。

## 4. 采集维度升级

### 4.1 数据模型 v2

四层实体：物理盘 disk → 卷 volume → 快照 snapshot → 条目 entry（文件与目录统一建模）。

**磁盘 / 卷级字段**（存入快照库 meta 表，key-value 形态，扩展不破坏兼容）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `volume_id` | 生成 `{serial}_P{index}` | 沿用 v1 规则，旧快照可直接对应 |
| `disk_serial` / `serial_source` | 手动 `-s` > smartctl > WMI | volume_id 稳定的前提；USB 桥下 WMI 不可靠 |
| `physical_model` / `physical_serial` | smartctl `-i` | 真盘型号/序列号；取不到则为空 |
| `bridge_model` | WMI `Model` | 原 v1 的 model 改名，明确标注它是桥 |
| `volume_serial_hex` | GetVolumeInformation（Win）/ blkid（Linux） | 格式化即定，换盘符后仍可认盘 |
| `partition_uuid` | GPT UUID / MBR 签名+偏移合成 | 多分区场景的稳定锚 |
| `partition_table_type` | GPT/MBR 探测 | 修复 v1 恒空的死字段；取不到写 `unknown` |
| `filesystem` / `volume_label` / `disk_capacity_bytes` / `partition_capacity_bytes` / `free_bytes` / `firmware` / `interface_type` | 平台层 | 沿用 v1 |
| `smart_*`（health / temperature_c / power_on_hours / reallocated_ct / pending_ct / raw_json） | smartctl `-H -A -j` | 可选；拿不到记 `smart_status=unavailable`，不阻断采集 |
| `os_platform` / `source_mount` | 平台层 | 盘符 → 挂载点泛化 |
| `scan_root` / `exclude_rules_json` / `hash_policy` | 本次采集参数 | 快照自描述采集口径；diff 前校验两次口径是否一致 |
| `collect_time_utc` / `collector_version` | — | 沿用 |

**条目级**（文件与目录统一建表）：

```sql
CREATE TABLE entries (
  entry_id        INTEGER PRIMARY KEY,
  parent_id       INTEGER NOT NULL,        -- 根为 0
  path            TEXT NOT NULL,           -- 相对路径，'/' 分隔，根为 '.'
  name            TEXT NOT NULL,
  depth           INTEGER NOT NULL,        -- 替代 v1 的 level_1..N
  type            TEXT NOT NULL CHECK (type IN ('file','dir','symlink','other')),
  size_bytes      INTEGER,                 -- 目录为 NULL
  allocated_bytes INTEGER,                 -- 簇对齐后的真实占用
  mtime_ns        INTEGER,
  ctime_ns        INTEGER,
  btime_ns        INTEGER,                 -- 创建时间（NTFS 等支持）
  attrs           INTEGER,                 -- Win 属性位掩码 / POSIX mode
  ext             TEXT,                    -- 小写扩展名（含点），无则 ''
  hash_algo       TEXT,                    -- NULL | 'sha256'（blake3 未实现）
  hash_hex        TEXT,
  hash_state      TEXT,                    -- 'full' | 'sampled' | 'error' | 'stale' | NULL
  path_norm       TEXT,                    -- casefold 后路径，跨文件系统比对用
  error           TEXT                     -- 采集该条目的非致命错误
);
CREATE UNIQUE INDEX uq_entries_path ON entries(path);
CREATE INDEX idx_entries_parent ON entries(parent_id, name);
CREATE INDEX idx_entries_ext_size ON entries(ext, size_bytes DESC);
CREATE INDEX idx_entries_mtime ON entries(mtime_ns);
CREATE INDEX idx_entries_pathnorm ON entries(path_norm);
CREATE INDEX idx_entries_hash ON entries(hash_hex) WHERE hash_hex IS NOT NULL;
```

要点与理由：

- **`path` + `parent_id` 双写**：`path` 支持前缀聚合与 LIKE，`parent_id` 支持递归 CTE 与懒加载列举；不引入 closure table。
- **目录全量成行**（v1 只记 empty_dir）：目录 mtime 可见、目录增删可 diff、du 可算。代价约 +5 万行 / 300 万文件，可忽略。
- **mtime 统一为 ns 整型**：避免字符串比较与时区/格式问题；`btime` 对判断"资料是哪批备份写入"有用。
- **`ext` 独立列**：把按类型统计/筛选从字符串函数变成索引扫描（3M 行下是秒级与分钟级的差别）。
- **`allocated_bytes`**：回答"盘为什么满了"比逻辑大小更准。
- **不采 atime**（现代系统 relatime 噪声大）；**不采 ACL/owner**（attrs 位掩码覆盖常用语义）。

**跳过记录**：

```sql
CREATE TABLE skipped (
  path         TEXT NOT NULL,
  warning_type TEXT NOT NULL,
  stage        TEXT NOT NULL,
  detail       TEXT,
  PRIMARY KEY (path, warning_type)
);
```

主键去重，结构性消灭 v1 的重复 ×2；reparse point（重解析点，含符号链接/联接）恒跳过并记账。

### 4.2 多分区与采集批次

- **粒度：每卷一个快照**；同一物理盘的多卷属于同一**采集批次 batch**。不做"每盘混合快照"——多文件系统混进一个 path 命名空间对 diff 与元数据只有害处。
- `volume_id` 沿用 `{serial}_P{index}`；同时记录 `partition_uuid`：分区表重排导致 index 变化时，靠它把新快照归并到正确卷，并在 catalog 留 volume_id 变更记录。
- 快照 ID：`<volume_id>/<yyyymmddTHHMMSSZ>`（UTC）。
- 流程：枚举该物理盘的全部卷（Win：CIM 关联；Linux：lsblk -J）→ **逐卷串行** scan → seal → copy_to_disk → register。串行是因为同一机械盘多卷并行扫描会磁头抖动，总耗时反而更长（不同物理盘并行放 P2 再议）。
- **部分失败**：单卷失败不中断批次，batch 记 `partial`，可对单卷重试；已成功卷的快照正常可用。无分区表/单卷盘是 `planned_volumes` 长度为 1 的特例。

### 4.3 采集工程

- **单遍 `os.scandir` 递归**：复用 DirEntry.stat 的目录列表期缓存，免掉 v1 每文件一次额外 `os.stat` 与第二遍 walk；预期采集耗时降至 v1 的 50–70%。
- **流式批量写入**：每 1–5 万行一个事务；建库期关闭索引与 journal，封库（seal）时一次性建索引、构建 dir_rollup、`PRAGMA optimize`。
- **断点续采**：`scan_journal` 记录已完成目录；中断后 resume 跳过已完成目录。续采日志放**侧车文件**而非主库内，避免与库同生共死；中断的快照目录标记 `incomplete`；已封库快照不可续采，只能新采。
- **过滤真正实现**：`--exclude-glob` 对相对路径按 fnmatch 语义匹配（支持 `**`），目录命中则整棵剪枝并记入 skipped；`--exclude-hidden` / `--include-system` 按 attrs 位判断。
- **错误记账**：所有跳过与异常入 skipped（结构去重）；采集结束输出摘要：文件数 / 目录数 / 跳过数 / 总字节 / 耗时 / 吞吐。
- 引擎与 CLI `cldm collect`、Web 采集任务共用同一入口。
- **实现注（2026-10）**：除上述外，现状还有——默认**不跨文件系统**（子挂载点整棵剪枝，`--cross-filesystems` 可放开）；目录级权限错误记 `scan_error` 不中断整次采集；扫描根下的 `_coldmanifest` 目录恒剪枝；`--all-partitions` 支持一次采整盘所有分区；断点续采（`--resume`，基于 scan_journal 侧车文件）与**数据根写锁**（DataRootLock，防止两个采集同时写同一数据根）均已实现。
- **硬盘盒（USB 桥）必须手填序列号**（2026-10 第八轮）：USB 盒会挡住真盘序列号（上报的盒 ID/占位号不能作为磁盘身份依据），因此判定为硬盘盒的盘**必须手动提供盘体标签序列号**才能采集——`collect_volume` 在 probe 后、scan 前判定（断点续采同样适用），不满足抛 `ManualSerialRequired`：API 提交 400、CLI rc=2（`--all-partitions` 批次一次判定整批拒绝）。**判定只看 `interface_type` 含 USB**（大小写不敏感；`bridge_model` 仅展示——Linux probe 会把 lsblk 盘型号填进 bridge_model，按它判定会把所有 Linux 盘误判为硬盘盒）；非 USB 盘不受影响，探测序列号不可用仍走 `VOL-{卷序列号hex}` 回退 + 强提示。提交前可用 `preflight_serial_required()`（`collect.py`）预检，`POST /api/collect/preflight` 也提前返回 `requires_manual_serial`。

### 4.4 磁盘元数据与平台层

- **平台抽象 probe 层**：Windows 沿用 CIM/PowerShell JSON（**删除脆弱的 wmic 回退**，失败直接报错）；Linux 用 `lsblk -J` / `blkid` / `udevadm`。macOS 不在范围内。
- **smartctl 为可选外部工具**：`smartctl -i -H -A -j`；USB 桥后常需 `-d sat` 等透传参数；拿不到记为 `unavailable`，**绝不阻断采集**。
- **实现注（2026-10 实机反馈后）**，SMART 采集口径如下（均在 `smart.py`）：
  - **设备名定位**（`smart_device_candidates` 候选链，`smart_device` 取首选）：优先级为环境变量 `CLDM_SMARTCTL_DEVICE` 直接覆盖（`source=env`）→ `smartctl --scan` 第 N 行（`source=scan`）→ `/dev/sdN`（`source=fallback-sd`）→ 盘符（`source=letter`）。候选链**去重保序，全部交给调用链依序尝试**，不是单选——映射不可用（盘不在扫描结果里，USB 桥常见）时多种设备形态都能试到，单选回退曾导致 USB 盘永远打不开。实测定案：`\\.\PhysicalDriveN` **不是 smartctl 认可的设备名**（只认 `/dev/sd[a-z]`、`/dev/sd[a-z][a-z]`、`/dev/pdN`、`X:`），裸传报 EINVAL `Invalid argument`、与 `-d` 无关，因此**已从候选链彻底移除**；Windows 上对 USB 桥要用 `--scan` 给出的 `/dev/sdN` + 扫描建议的 `-d sat` 才读得到。
  - **设备与类型的权威来源**（`scan_devices` / `parse_scan_output`，2026-10 第五轮修订）：优先 `smartctl --scan-open -j`（逐台真实打开设备，能顺带给出可用性与正确的 `-d` 类型），回退 `--scan -j`、文本 `--scan`；同时支持 `smartctl --scan -j` 的 JSON（`{"devices":[{"name","type",...}]}`，name 缺失回退 info_name；smartctl 7.5 起）与纯文本行（`/dev/sdc -d sat # ...`）。结果进程内缓存（`reset_scan_cache` 可清），但**只缓存非空结果**——空结果（smartctl 缺失/刚启动盘未就绪/权限等瞬时失败）绝不进缓存，原地重试一次后仍空则直接返回，等下次调用再试；否则一次瞬时失败会把整个服务进程的映射永久污染成空（"第一次好、后面坏"）。`--scan-open` 对打不开的设备附 `open_error`（权限/休眠等）——这些条目映射不可靠，跳过不进映射表。
  - **类型兜底链**（`_device_types` / `_BRIDGE_TYPES`，2026-10 第五轮修订）：Windows 顺序为**扫描建议类型 → `sat` → `sat,12` → `sat,auto` → 桥专用（`usbjmicron` / `usbjmicron,p` / `usbjmicron,x` / `usbsunplus` / `usbprolific`）→ 空类型（auto，末位兜底）**；Linux 顺序为 auto → sat → sat,12 → 扫描建议 → 桥专用。去重后逐次试，第一次读到 JSON 且退出码低 2 位无致命错误即返回（`-d sat` 是 smartctl 的"通过 USB 桥按 SATA(ATA 透传)协议读"参数；不同桥芯片还各有专用参数，所以才有这条链）。Windows 上 `auto` 会把 USB 桥误判成走错通路（报 `Invalid argument`）而手工 `-d sat` 能读出真数据，故 `sat` 必须先于 `auto`。**安全红线**：`jms56x` / `jmb39x` / `sntjmicron` 是 RAID 盒专用类型（会向 RAID 卷某 LBA 写），对普通单盘有**覆写扇区风险**，一律不进兜底链；`usbjmicron(,p/,x)` 等只在确认芯片时命中，安全。`read_smart_verbose(devices=[...])` 对候选链里**每台设备**都走完整类型链。
  - **ATA 属性表与关键 HDD 指标采集口径**（`ATA_CONTRACT_KEYS` / `_parse_ata_attributes` / `parse_smart`，2026-10 第五轮）：机械盘（SATA/ATA）的 `ata_smart_attributes.table` 规整为列表，每项 `{id, name, value, worst, thresh, raw_value, raw_string, when_failed}`——**raw_value 解析规则**：优先 `raw.string` 里可解析的整数（48-bit 多字时 smartctl 已拼好十进制串，`raw.value` 只是低字），回退 `raw.value`，都解析不了置 null（`raw_string` 保留原文）。关键指标按属性 ID 映射取 raw 值：power_cycle_count(12) / load_cycle_count(193) / udma_crc_errors(199) / raw_read_error_rate(1) / seek_error_rate(7) / spin_retry_count(10) / power_off_retract_count(192) / airflow_temperature_c(190) / head_flying_hours(240)；身份/链路细节取自 JSON 顶层字段：interface_speed_current / interface_speed_max（`interface_speed.{current,max}.string`）、sata_version / ata_version（`.string`）、trim（`trim.supported`，bool）、zoned（`zoned_device`）、model_family、rotation_rate（转速 rpm，SSD 为 0/缺失）、form_factor（如 `2.5 inches`）——契约共 **18 键 + ata_attributes**。**落库**：`disk_smart` 表增 19 列（`ata_json` 存整表 JSON + 18 个扁平键），旧库幂等迁移自动补列；采集 meta 记 `smart_ata_json`。**API 契约**：`GET /api/disks/{id}`、`GET /api/disks/{id}/smart`、`POST /api/disks/{id}/smart/read` 响应均带 `ata` 契约（`ata_attributes` + 18 键，缺项 null/[]/false；`ata_attributes` 由 `ata_contract` 冻结键集统一生成）——**磁盘详情端点顶层与 `latest_smart` 内层两层都有**，与 `ssd` 契约同构。**快照报告**：HTML 报告 SMART 段新增「SMART 关键指标」表 + 属性表前 20 行（catalog 历史行优先，meta 兜底；无数据不渲染）。
  - **exit_status 位掩码语义**（`_usable`）：bit0(1)=命令行错误、bit1(2)=设备打不开 → 视为失败；bit3(8)=盘报 SMART FAILING、bit4–7(16/32/64/128)=预失败/历史告警 → **有数据就算成功**，健康等级由 `parse_smart` 按这些位推断为 failed / warning。
  - **容量软校验**（`_capacity_screen`）：`--scan` 行序与 PhysicalDrive 编号一致只是假设，扫描映射可能错位。现场读取前先对 scan 来源候选用 `smartctl -i` 读实际容量，与盘的已知容量差 **>20%** 时剔除该候选（降级到 `/dev/sdN` fallback 形态）并在结果 `scan_info.capacity_check` 标 `mismatch`；任一方容量未知则不校验；候选全被剔除时保留原候选（宁可试错也不空手）。
  - **解析新字段**（`parse_smart`）：health / temperature_c / power_on_hours / reallocated_ct / pending_ct / start_stop_ct / spin_up_ms / device_type / model / serial / firmware / capacity_bytes / rotation_rate / form_factor，缺失一律 None、坏 JSON 不抛异常；字段写入 meta 的 `smart_*` 键。
  - **尝试记录与错误分类**：无论成败，meta 均可含 `smart_attempts_json`（每次尝试的 argv/退出码/stderr 片段 + `-j` 失败响应里 `messages[].string` 提取的人话——`-j` 出错时 stdout 仍是 JSON、stderr 往往为空，真因在 messages 里），失败原因分类（`_classify_attempts`）：timeout / not_found → **bit1(2)=设备打不开 → `device_open`** → **bit0(1)=命令行错误 → `cmdline_error`** → stderr/messages 正则匹配 permission_denied / device_type_unknown / not_found → other，每类配可执行建议（磁盘页「现在读取 SMART」直接展示，含每次设备串与 stderr 摘要）。**bit1 优先于 bit0**：跨多次尝试时"设备打不开"更接近真实原因（一次参数错常伴随一连串打不开，只看最后一次会把参数错当结论），故先全量找 bit1，找不到才用 bit0。
  - **现场读取与 preflight 走完整候选链**：磁盘页「现在读取 SMART」（`POST /api/disks/{id}/smart/read`）与采集前检查（`POST /api/collect/preflight`）都用 `device_candidates_for_path`（有盘号走 `smart_device_candidates` 全链：扫描映射 + `/dev/sdN`；只有盘符时退化为盘符形态）拿到完整候选链再逐个尝试——第三轮前单选一个设备曾导致 USB 桥盘在现场读取时永远打不开。
  - **映射结论**（`scan_info`）：`read_smart_verbose` 返回扫描到的设备表、候选链及各自 source、实际生效设备串、是否经扫描映射成功（`mapped_from_scan`）；采集时落 meta `smart_scan_info_json`，供磁盘页展示"哪块物理盘对应哪个设备串"。
  - **磁盘身份校验**（第七轮，PR-B/PR-C：`read_device_identity` / `_score_identity_match` / `resolve_smart_device` / catalog 冲突检测 / `identity_audit.py`）：同型号同容量多盘时，`smartctl --scan` 的行序下标映射可能错位——把另一块盘的 SMART 与序列号当成目标盘写进快照（甚至污染 disk_id 导致两块盘静默合并成一行）。本轮改为**按序列号认盘**：
    - **认盘规则**（`resolve_smart_device`，2026-10 第八轮修订）：环境覆盖（`CLDM_SMARTCTL_DEVICE`，`mapped_by=env_override`）优先；否则枚举扫描表**全部条目**，逐台 `smartctl -i -j` 读身份（serial/model/capacity，同一次调用内按设备缓存），与期望序列号/容量/型号打分排序——serial 精确匹配 100 / 容量差 ≤5% 且型号一致：读到真序列号 90、读不到 80 / 型号**明确不一致**（同容量可区分）70 / 型号不可比 20 / **容量差 >20% → 0（判另一块盘，直接剔除）**。**唯一性判据 `unique_capacity_match`**：top 唯一且 ≥70 且领先第二名 ≥10 → 视为验证通过（盒 ID 与真盘序列号不同没关系——容量/型号能唯一定位即可；**同型号同容量并列 → 仍不验证**）。`/dev/sdN` 下标回退形态标 `risk=unverified_index_mapping`（下标映射未经验证），盘符候选殿后。多台报同一序列号、或多台弱匹配且都读不到序列号 → `scan_info.identity_ambiguity` 记中文歧义原因与建议（拔掉一块再采 / `--serial` 显式区分）。`mapped_by ∈ serial_match|unique_capacity_match|capacity_match|env_override|fallback`，`scan_info.identity_reason` 给人话解释（盒 ID + 容量 + 真盘序列号，或盒 ID + 容量/型号唯一定位）。
    - **序列号覆盖规则**（Windows `probe/windows.py` 与 Linux `probe/linux.py` 口径一致）：**只有身份校验通过**（`mapped_by ∈ serial_match|env_override` 且无歧义）才允许 smartctl 序列号覆盖 probe 值（`serial_source=smartctl`）；未验证时 smartctl 序列号只允许"补全"（probe 没有时写入，`serial_source=smartctl_unverified`），否则**保留探测值 + warning「为防错盘已保留探测值」**，smartctl 读到的值放 `physical_serial` 供比对。
    - **注册层冲突检测**（`catalog.py` `ensure_disk` + `schema.py`）：`disks` 表增 `identity_verified`（NULL/1/0）与 `identity_conflict_json`（冲突记录，最多保留最近 20 条）。命中冲突（容量差 >20% / 型号归一化后不同 / 可用序列号不同）时**不覆盖任何既有字段**，置 `identity_verified=0` 并返回冲突清单；`collect._register_catalog` 把冲突产成 warning。
    - **meta 新键**（`collect._write_meta`，仅在有值时写）：`identity_verified`(1/0)、`identity_risk`、`identity_ambiguity`、`identity_warnings_json`。
    - **体检工具**（`identity_audit.py`，纯只读，不改任何库/文件）：`audit_identities(data_root)` 用快照库里现存的序列号证据做"串盘"追溯——告警类型（2026-10 第八轮口径）：`cross_disk_serial_alias`（high，快照的 disk_serial/physical_serial 其实是**另一块盘**的已知序列号——最具体的串盘信号，优先级最高）、`intra_snapshot_serial_drift`（high，同一快照内不同来源的序列号互相矛盾）、`inter_snapshot_serial_volatility`（high，同一 volume_id 的多次快照之间**逐字段**比较可用序列号/型号/容量变了）、`high_fallback_ratio`（medium，某盘过半快照走了未验证回退）、`fallback_minority`（low，有快照走未验证回退但未过半——信息性提示）；USB 桥正常形态（盒 ID 与真盘序列号并存）不再报 HIGH，记 notes。告警去重；summary 按 high/medium/low 三档计数。返回 alerts / affected_disk_ids / summary / warnings，库缺失/未封库/meta 缺键等一律计入 warnings 不抛异常。CLI `cldm identity-check --data-root [--json]`（退出码 0 无高危 / 1 有高危 / 2 错误）；API `GET /api/identity-audit`。
    - **身份状态派生**（`identity_audit.disk_identity_status`）：`verified|unverified|conflict|unknown` + 中文理由；未验证时给出**具体原因**——读最新快照 meta 的 `identity_reason` / `identity_warnings(_json)` 首条（单条 LIMIT 1 查询，满足磁盘列表逐行调用）。出现在 `GET /api/disks`（列表，`identity_status`/`identity_status_reason`）、`GET /api/disks/{id}` 与快照列表/详情（取自关联盘，无关联盘 → unknown）。前端 `IdentityStatusBadge` 四态徽标（磁盘列表「身份」列 / 磁盘详情身份卡 / 快照详情「磁盘身份」行，unknown 不显示）。
    - **现场读取防错盘**（`POST /api/disks/{id}/smart/read`）：读到设备序列号与期望不一致（且定位确实走过身份解析）→ `ok=false`、`reason=identity_mismatch`、message 说明读到的盘与建议（拔掉同型号盘 / `--serial` 固定）。
    - **硬盘盒手填序列号与身份编辑入口**（2026-10 第八轮）：
      - **采集闸**：`_is_usb_bridge`（`collect.py`，只看 `interface_type` 含 USB）判定硬盘盒 → 必须手填盘体序列号，否则 `ManualSerialRequired`（API 400 / CLI rc=2，含批次；`--resume` 同样适用）；`POST /api/collect/preflight` 新增 `requires_manual_serial` / `manual_serial_reason` / `probe_serial` / `bridge_model` / `interface_type`，前端依赖检查据此禁用「开始采集」。
      - **身份编辑**（`PATCH /api/disks/{id}` 扩展，原仅 nickname）：`identity_verified`（手动确认/撤销，记 `identity_verified_source='manual'` + `identity_verified_at` UTC ISO）、`physical_serial`（记录性字段，可直接改）、`disk_serial`——**仅零快照盘可改**（它是 disk_id / 卷 ID 的派生源，有快照 → 400 人话指引；零快照时级联更新 disk_id / 卷 / 卷 ID 前缀 / disk_smart）。`disks` 表新增 `identity_verified_source`(auto|manual) / `identity_verified_at`（幂等迁移）。
      - **现场重新校验**（`POST /api/disks/{id}/identity/recheck`）：盘接上后现场重读并判定（serial_match / unique_capacity_match 与 probe 同判据），三态 `verified|unverified|not_attached`；通过时 `identity_verified=1`（source=auto）并顺带更正读到的不同真盘序列号，未通过置 0 并给原因。
  - **SSD 专属指标采集口径**（`parse_ssd` / `ssd_contract`，2026-10 第四轮）：机械盘的 SMART 属性对 SSD 意义有限，SSD 的关键健康信号在另一组指标上，因此单独解析出一个 `ssd` 子字典：
    - **NVMe 盘**：从 `nvme_smart_health_information_log` 段取 `percentage_used`（换算 `life_left_pct = 100 − percentage_used`，截到 0–100）、`available_spare`（备用空间百分比，另存阈值 `available_spare_threshold`）、`data_units_read/written`（**1 unit = 1000 × 512B**，换算成 `read_bytes` / `written_bytes` 并折算 TB 保留两位）、`media_errors`（介质错误数）、`unsafe_shutdowns`（异常断电次数）、`power_cycles`（通电次数）、`controller_busy_time`（控制器忙时，**单位分钟**）、`temperature_sensors`（多温度探头数组）；`source="nvme"`。
    - **SATA/ATA SSD**：按属性 ID 取——Total_LBAs_Written(241) / Total_LBAs_Read(242) 换算字节（×512；部分盘报 32MiB 单位但 smartmontools 未标注、无法可靠区分，按 LBA 口径换算，解析不了就留空不猜）、寿命属性 SSU_Life_Left(231) / Media_Wearout_Indicator(233) / Percent_Lifetime_Remain(202) 取首个可换算者作 `life_left_pct`、Wear_Leveling_Count(177)；有任何 SSD 属性才判定为 SSD（`source="ata"`）。
    - **落库**：`disk_smart` 表增 10 列（`life_left_pct`、`percentage_used`、`available_spare_pct`、`written_bytes`、`read_bytes`、`media_errors`、`unsafe_shutdowns`、`power_cycles`、`controller_busy_minutes`、`ssd_json` 兜底），旧库幂等迁移自动补列；采集 meta 记 `smart_ssd_json`（旧快照无此键，展示层回退读 catalog 行的 `ssd_json`）。
    - **API 契约**：`GET /api/disks/{id}`、`GET /api/disks/{id}/smart`、`POST /api/disks/{id}/smart/read` 的响应都带 `ssd` 字段（冻结键集，缺项 null/[]）；**磁盘详情端点顶层与 `latest_smart` 内层两层都有**——前端健康卡读的是 `latest_smart.ssd` 这一层。
    - **快照报告**：快照自包含 HTML 报告在 SMART 段展示「剩余寿命 / 累计写入 / 累计读取」。
  - 可用 `CLDM_SMARTCTL` 指定 smartctl 路径、`CLDM_SMARTCTL_ARGS` 透传额外参数。
- **真盘识别**：优先 smartctl 的 model/serial；WMI 的型号记为 `bridge_model`；serial 最终以手动 `-s` 兜底（沿用 v1 约定）。
- **盘符校验修复**：校验目标是"卷存在且为固定/可移动磁盘"，替换 v1 的 `os.path.exists("E:")` 弱检查。

### 4.5 哈希策略（默认关闭，按需启用）

| 策略 | 成本 | 能回答 | 不能回答 |
|---|---|---|---|
| `none`（默认） | 0 | 增删、size/mtime 变化 | 同尺寸同时间戳的改写、静默损坏、查重、改名 |
| `sampled`（如 1% + 全部 >1GB） | 分钟级 | 抽样式巡检 | 全量保证 |
| `full`（轮换/年检前执行） | 机械盘顺序读约 3h 起 | 完整校验、精确查重、改名/移动检测 | — |

- 哈希做成**独立命令/任务**（`cldm hash`），不是采集必经步骤；按行批量事务提交，天然断点续算，并带 `(size, mtime, path)` 级缓存表 `hash_cache`（重复计算直接命中）。
- 算法：sha256（标准库，默认）。blake3 / xxhash **未实现（我方建议不做：瓶颈在磁盘读速而非哈希计算）**。
- **sampled 指纹为 v2**：首 / 中 / 尾各 64KB + 算法与文件大小混入指纹串（旧 v1 仅首尾，仍按 sampled 档参与但不产生内容结论）。
- **查重联动**：`cldm hash --candidates` 只对「大小重复」的文件补算哈希（为查重服务，省时间）；`--group <hash>` 对单组重复文件做全量精验。
- **增量复用**：`(size_bytes, mtime_ns, path)` 未变则继承上一快照哈希；变了标 `stale`，由 `cldm hash` 补齐。
- 未启用哈希时，diff 的 `content_changed` / `moved_or_renamed` 返回 `null`（无证据），**不谎报为"无变化"**；启用后也只信 `full` 哈希（sampled / 错误状态一律回退 size/mtime 语义）。

### 4.6 盘上备份

- 路径模板（settings 可改）：`<卷根>\_coldmanifest\<volume_id>\<ts>\snapshot.db`，附带旁车 `snapshot.json`（volume_id、采集时间、文件数、总字节、collector_version——没有工具时肉眼也能看懂这份清单）。
- **原子性**：先写 `snapshot.db.tmp`，流式拷贝同时计算 sha256，与主机副本 hash 一致后 `os.replace` 改名，再写 json。任何一步失败，`.tmp` 残留可安全重跑；改名在 NTFS/exFAT 上同为元数据操作。
- **空间不足**：任务记警告 `on_disk_copy=skipped(no_space)`，不影响整批成功（主机副本已是完整制品）。
- 多分区盘每卷的副本写在**各自卷的根下**，不跨卷写。
- 用途：(a) 主机数据目录损毁时的恢复源；(b) 盘接入无主机副本的机器时 `cldm import-db` 就地登记使用；(c) 异地场景"盘 + 清单"一体冷存。
- 校验：`cldm verify-copy <sid>` 重算盘上副本 hash 对账（支持抽样 `--sample` 与全量 `--full`）；卷详情页展示副本状态（存在 / 缺失 / 校验时间）。
- **实现注（2026-10）**：盘上副本**不做压缩**（用户决定默认不压缩，`.zst` 未实现）；`cldm import-db` 已实现——把盘上/外部 snapshot.db 就地登记进 catalog（默认 `--in-place` 直接引用原路径，`--copy` 才拷入数据根），无需主机副本即可浏览。

## 5. 存储设计

### 5.1 快照库 snapshot.db

表：entries（见 4.1）、skipped（见 4.1）、meta、dir_rollup：

```sql
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT);      -- 4.1 的全部盘/卷字段

CREATE TABLE dir_rollup(
  entry_id        INTEGER PRIMARY KEY,   -- 仅目录
  file_count      INTEGER NOT NULL,
  dir_count       INTEGER NOT NULL,
  total_bytes     INTEGER NOT NULL,      -- 递归逻辑大小
  total_allocated INTEGER NOT NULL,
  max_mtime_ns    INTEGER                -- 目录树下最新 mtime
);
```

- **dir_rollup 封库时一次性自底向上聚合**（单遍递归 CTE，3M 行约数秒）：du、目录级 diff 汇总、"最近变化的目录"全部变成单表查询。
- 全文搜索（P2）：`CREATE VIRTUAL TABLE entries_fts USING fts5(name, path, content='entries', content_rowid='entry_id')`；FTS5 不可用的环境降级 LIKE。建索引成本约 +10–15% 体积。
- 打开方式：`file:<path>?mode=ro`（普通只读）。**不用 `immutable=1`**——它向 SQLite 声明"文件永不变化"，但封库后哈希回填（hash）、FTS/统计补建（build-fts / build-stats）仍会就地写库；immutable 连接在这些写入后会读到错乱页，报假的 "database disk image is malformed"（文件其实没坏，重启服务即恢复）。配套约束：写快照库的任务必须在写前、写后把连接池里该快照的连接逐出（`AppState.evict_snapshot`），读到坏页时可 `cldm integrity-check <快照ID>` 自查（只读 PRAGMA quick_check，退出码 0 正常 / 1 损坏）。

### 5.2 catalog.db（注册表 + 统计缓存）

**不存 entries**；损毁后可从 `data/` 目录扫描 + 各快照库 meta 重建——**已实现**：`cldm rebuild-catalog`（支持 `--dry-run` 预览，冲突以快照库 meta 为准并回填 catalog）。除下方列出的表外，实际还有三张：`hash_cache`（哈希结果缓存，见 §4.5）、`stats_precomputed`（封库期预计算的快照统计，列表/详情直读）、`disk_smart`（SMART 结构化记录，供趋势查询）。

### 5.3 diff 物化库

diff 作为后台任务执行（ATTACH 两库 SQL join），结果写入 `data/_diffs/<diff_id>.db`：

```sql
CREATE TABLE diff_meta(key TEXT PRIMARY KEY, value TEXT);  -- a,b,options,duration,summary_json
CREATE TABLE diff_entries(
  id INTEGER PRIMARY KEY,
  change_type TEXT NOT NULL,   -- added/removed/size_changed/mtime_changed/
                               -- content_changed/moved_or_renamed/type_changed/identical
  path TEXT NOT NULL, path_norm TEXT NOT NULL,
  depth INTEGER NOT NULL,
  a_entry_id INTEGER, b_entry_id INTEGER,
  a_size INTEGER, b_size INTEGER,
  a_mtime_ns INTEGER, b_mtime_ns INTEGER
);
CREATE INDEX idx_de_type_path ON diff_entries(change_type, path);
CREATE INDEX idx_de_path ON diff_entries(path);
```

**为什么物化而非实时 join**：Web 场景下 diff 结果要被反复翻页、按类型/路径过滤、排序、导出；实时 join 意味着每个动作重跑 40–60 秒的 3M×3M join，不可接受。物化后全部是索引查询。代价是每 diff 一个几十至几百 MB 的结果库（identical 行默认不落库、只计数；显式 `show_identical` 才落）。`depth` 降级为查询期过滤条件，不再影响 join 本身。≤20 快照 ⇒ diff 组有界（C(20,2)=190，实际远少），幂等复用结果库，总量可控。

CLI `cldm diff` 同步执行同一引擎，退出码：`0` 无差异 / `1` 有差异 / `2` 错误。
> 实现注（2026-10）：diff_entries 实际还有 `a_hash / b_hash / b_path` 列（哈希证据与改名后的 B 侧新路径；旧结果库无这些列，读取层探测兼容）；diff_meta 里物化时写入 `evidence_level / evidence_json`（见 §6.3）与 `hints_json`（Windows 大小写改名提示，见下）。

### 5.4 性能预算（3M 文件盘）

| 操作 | 目标 |
|---|---|
| 采集（无哈希） | ≤ v1 的 70% 耗时 |
| 快照列表 / 首页加载 | < 300ms |
| stats / du / tree 查询 | < 2s |
| 搜索（前缀模式） | < 1s |

```

`evidence_level` 明示本次对比整体结论依据（`size+mtime` / `hash`）；且每个分类都有**逐分类 evidence**（该结论是按哈希还是按大小/时间判的，物化时写入 diff_meta，API / CLI / HTML 报告均展示）。未启用哈希时 `content_changed` / `moved_or_renamed` 为 `null` 而非 0。

**Windows 大小写改名提示（hints）**：Windows（NTFS）文件名不分大小写，用户把 `a.txt` 改名为 `A.TXT` 后做默认（精确路径）对比，会显示为"1 删除 + 1 新增"。若两侧快照任一来自 win32（快照 meta 的 `os_platform` 键，采集时写入；旧快照无该键则不提示）且本次未启用 `case_insensitive`，物化时写 `hints_json`，API create/detail 响应带 `hints` 数组、CLI 在结果末尾输出提示行（说明"仅大小写改名会显示为 1 删除 + 1 新增，可加 `--case-insensitive` 归并"）；启用 case_insensitive 后提示消失且改名正确配对。相关：采集时若扫描根路径超过 200 字符（Windows 长路径边界），记 skipped（`warning_type='long_path'`）并提示启用系统长路径支持。

SSE 事件流（`GET /api/tasks/{task_id}/events`）：

```

       "bytes":1412000000000,"rate_mb_s":96,"current_dir":"/photos/2023","eta_s":240}

### 6.4 分页与计数策略

- **一律 keyset（游标）分页，禁用 OFFSET**：3M 行的 `OFFSET 2000000` 是全扫描。游标键随排序列：`size_desc` → `(size_bytes DESC, entry_id)`；`name` → `(name COLLATE NOCASE, entry_id)`；父目录内列举 → `(parent_id, name, entry_id)` 命中 `idx_entries_parent`。`limit` 上限 500，默认 200。
- **计数分层供给，绝不每页 COUNT(*)**：
  - 快照级总数：采集时预计算入 catalog；
  - 目录级直接子节点数：父目录请求时顺带算（单目录子项通常 ≤ 数千，索引范围 count 毫秒级）；递归数走 dir_rollup；
  - 带过滤的全局列表：只返 `has_more` + `next_cursor`，前端用"加载更多"；确需总数时显式 `?count=exact`（百毫秒级，按需）。
- du 一律查 dir_rollup，不在请求期跑递归 CTE；FTS 搜索同理只取前 N + 游标。

### 6.5 任务模型

- **collect 任务**：POST 启动 → 后台线程执行（CPU 轻、IO 重，单线程足够）→ SSE 进度（files/dirs/bytes/rate/current_dir/eta；总数未知时呈现已扫描量+速率，不伪造百分比）→ 可取消；取消＝**丢弃本次采集并保留现场供续采**（未封库的快照目录保留并标 incomplete，只清理盘上 `_coldmanifest` tmp 残留，启动时也会清扫 tmp）；已扫描进度通过 scan_journal 侧车文件保留，用 `cldm collect --resume`（或 API `resume: true`）从断点续采——续采结果与一次跑通逐条一致（实测验证过）。没有「暂停/继续」语义。
- **diff 任务**：POST（幂等键 `(a, b, options_hash)`）→ 后台物化 → 查询；同一对快照+参数重复发起直接复用结果。
- 任务页支持对运行中任务取消，进度走 SSE 事件流。
- **任务删除**：`DELETE /api/tasks/{task_id}`（或 CLI `cldm task-delete <task_id>`）——仅终态任务（done/error/cancelled）可删，运行中/排队中返回 409；只删 catalog.tasks 登记行，**不级联**快照/对比/文件（快照有独立删除入口）。典型场景：快照删掉后任务跳转 404，把任务行清掉。
- **TaskRunner 连接模型**：工作线程写路径持 `_lock` 共用同一 catalog 连接（见 §4.2/记忆口径：CAS 认领、进度回调、终态回写全程持锁）；API 线程读路径（查任务/列表/批次/取消首次读）改走每次独立的短连接（`uri=True` + `Row` + `busy_timeout=5000`）——sqlite3.Connection 非线程安全，API 线程与工作线程并发用同一连接会偶发 `sqlite3.InterfaceError`（表现为任务运行 + 页面轮询时 GET /api/tasks 500）；WAL 模式下读写互不阻塞，catalog 读都很小，短连接开销可忽略。
- CLI 与 Web 共用引擎：CLI 采完的快照同样自动登记 catalog（若数据根一致）。

### 6.6 安全与网络

默认开放局域网访问、不设鉴权（信任内网环境）；生产同源不开 CORS；导入路径白名单 + 符号链接解析后前缀校验；API 无"读任意文件"端点。详见 3.4。

## 附录：名词注释

- **keyset 游标分页**：用"上一页最后一条的排序键"继续取下一页，避免深 OFFSET 的全表扫描。
- **SSE（Server-Sent Events）**：基于普通 HTTP 的服务端单向推送，用于任务进度。
- **immutable=1**：SQLite 只读打开参数，声明文件不再变化，跳过锁与缓存校验。本项目**已弃用**：快照封库后仍会被哈希/补建任务就地写，immutable 的前提不成立，曾导致"假损坏"（malformed 报错、重启即好）；全部读路径已改 `mode=ro`。
- **WAL**：SQLite 的写前日志模式，读写并发更好。
- **FTS5**：SQLite 的全文索引模块。
- **dir_rollup**：目录递归聚合物化表（本设计术语，封库时构建）。
- **path_norm**：大小写归一后的路径列，用于 NTFS / ext4 之间的大小写语义差异比对。
- **lsblk / blkid**：Linux 下列出块设备与文件系统信息的工具。
- **smartctl**：smartmontools 提供的硬盘 SMART 读取工具；`-d sat` 是其 USB 桥透传参数。

### A.2 CLI 全量子命令（`cldm`）

`serve` · `collect`（含 `--resume` / `--cross-filesystems` / `--all-partitions`；**USB 硬盘盒必须 `--serial` 手填盘体序列号，否则 rc=2**）· `import-legacy` · `import-db`（`--in-place` / `--copy`）· `diff`（`--hash --case-insensitive --ignore-mtime --ignore-size --show-identical`）· `export`（csv / v1_csv）· `report`（HTML）· `build-fts` · `build-stats` · `hash`（`--policy full|sampled --candidates --group --limit --root`）· `duplicates`（`--mode content|name|fingerprint`）· `verify-copy`（`--sample --full`）· `delete`（`--on-disk keep|delete --force`）· `nickname disk|volume <id> [名字]`（设置/清除昵称）· `integrity-check <快照ID>`（或 `--all`；只读 quick_check，退出码 0 正常 / 1 损坏）· `identity-check --data-root`（`--json` 可选；磁盘身份体检只读，退出码 0 无高危 / 1 有高危 / 2 错误）· `task-delete <task_id>`（删除终态任务登记行；未知/运行中退出码 2）· `rebuild-catalog`（`--dry-run`）
