# 10M 条目规模压测报告（P1 收尾 · P2 性能基线）

> 日期：2026-09-30 · 环境：WSL2 Linux，4 核 / 5.8 GiB RAM / ext4（/dev/sdd, 40 GB），
> Python 3.12.3（.venv-wsl），SQLite 3.45（trigram 可用）。
> 所有压测数据在 `/tmp/opencode/bench10m`，dev 数据根未触碰；API 测量走 TestClient 进程内（未碰 8765/5173）。
> 代码零改动：本轮只加压测脚本（`scripts/bench10m_*.py`），`src/` 未动，全量 pytest 198 passed。

## 0. 结论速览

| 结论 | 说明 |
|---|---|
| **P0 查询指标在 10M 全部保持毫秒级** | entries/tree/du/搜索/翻页 1–30 ms，与 3M 时基本持平（keyset、dir_rollup 预计算的设计收益） |
| **唯一超标项：stats 聚合 6.4–9.6 s** | 目标 <2s 是 3M 口径；10M 下线性放大到 6–10 s，且峰值 RSS 1.58 GiB（temp_store=MEMORY）。建议 P2 在封库期预计算（快照不可变，直方图可静态化） |
| **diff 物化随条目数线性放大** | 10M×2 归并 369–429 s（18 µs/行对），瓶颈是 Python 归并循环；`_pair_moved`（含 100 万重复内容候选对）仅 1.2 s，不是热点。P2 可把归并下推 SQL，预估 3–5× |
| **seal 流水线 10M 约 3.4 min** | 索引 43 s + dir_rollup 45 s + optimize 3.4 s + FTS 108 s；FTS 索引 3.31 GiB（落在 oracle 预估 2–4 GB 区间内） |
| **采集/哈希吞吐** | 热缓存 ext4：采集 2.9 万条目/s（真盘 / 实测）、哈希 full 2.1 万文件/s（小文件、开销主导）。**冷机械盘会慢一个数量级以上，这正是"3M 真盘 ≤ v1 70%"验收要在 Windows 真盘上补验的原因**（见 §8） |

## 1. 数据集与方法学

不造 1000 万真实文件，直接 SQL 批量生成快照库（`scripts/bench10m_make.py`，可复现 seed=42）：

- **B1**：10,000,000 条目 = root('.') + 300,000 目录（最深层 11）+ 9,699,999 文件（最深层 12）。
  路径唯一且 parent_id 与路径严格一致（生成后有孤儿/路径一致性校验，均 0）；
  size 8% 零字节、其余对数均匀分布；mtime 2015–2026 随机；ext 按规则表；
  path_norm=casefold；全部文件带 hash_state='full' 的随机 sha256。
- **B2**（`cp` B1 后 SQL 施加改动，合计 ~1.9%，各集合互斥）：
  size 改 5 万（hash 同步换）· mtime 改 5 万（hash 不变）· 删除 5 万 · 新增 5 万 ·
  改名 2 万（path 加 `.ren`，内容不变）· 同尺寸同 mtime 只换 hash 2 万 ·
  另有删除/新增各 1000 条共享同一 (hash, size)，专门给 `_pair_moved` 制造 1000×1000=100 万候选对。
- 期望 diff 计数（hash=sha256）：content_changed 70,000 · mtime_changed 50,000 ·
  moved_or_renamed 21,000 · added/removed 各 49,000 · identical 9,810,000。**实测逐项吻合**。
- 复现命令：

```bash
.venv-wsl/bin/python scripts/bench10m_make.py /tmp/opencode/bench10m   # 造数+注册 catalog（约 50s）
.venv-wsl/bin/python scripts/bench10m_seal.py /tmp/opencode/bench10m --no-fts   # 封库分步计时
.venv-wsl/bin/python -m cold_manifest build-fts BENCH10M_P0/20260928T000001Z --data-root /tmp/opencode/bench10m
.venv-wsl/bin/python scripts/bench10m_query.py /tmp/opencode/bench10m
.venv-wsl/bin/python -m cold_manifest diff BENCH10M_P0/20260928T000001Z BENCH10M_P0/20260928T000002Z --hash sha256 --data-root /tmp/opencode/bench10m
.venv-wsl/bin/python scripts/bench10m_report.py /tmp/opencode/bench10m
```

> 注：压测结束后 B2 库（5.8 GiB）已删以释放磁盘；`make` 脚本幂等，重跑约 2 min 可完整还原。

## 2. seal 流水线（10M，两代快照）

| 步骤 | B1 实测 | B2 实测 | db 体积（步后） |
|---|---|---|---|
| 数据灌入（make） | 44.0 s | 改动施加 3.0 s | 2.8 GiB |
| 建索引（8 个） | 43.0 s | 45.7 s | 5.43 GiB（+2.7 GiB） |
| dir_rollup | 45.5 s¹ | 46.3 s | +9 MiB |
| PRAGMA optimize | 3.4 s | 3.2 s | — |
| FTS5（trigram，`build-fts` 单独跑） | 108.5 s | —（跳过省盘） | **8.75 GiB（FTS +3.31 GiB）** |
| **合计（含 FTS）** | **≈3.4 min** | | 峰值 RSS 21 MiB |

¹ 首次实测（页缓存热）曾为 9.6 s；本轮为冷缓存数字，作为保守口径。

- 3M 导入基线是 1069.9 s（含 CSV 导入全程）；10M 生成+封库全程约 4 min，**FTS 构建占一半**。
- **FTS 体积 3.31 GiB / 10M 条目**，与 oracle 预估 2–4 GB 一致；库总体积 8.75 GiB ≈ 原始数据的 3.2×（索引+全文索引），**容量规划按"快照条目数 × 900 字节"估比较好**。

## 4. diff（B1 vs B2，物化 19 万变更行 + 100 万 moved 候选对）

| 指标 | hash=sha256 | hash=none | 目标/说明 |
|---|---|---|---|
| 物化耗时 | 428.9 s（首次）/ 369.1 s（force 复测） | 382.4 s | P0 基线 <60 s 是 3M 口径；10M ≈ 6–7 min，**线性于条目数**（369 s ÷ 2000 万行对 ≈ 18 µs/行） |
| 峰值 RSS | **54 MiB** | 52 MiB | 流式归并，内存 O(1)，✅ |
| 计数正确性 | 与期望**逐项一致**（70k/50k/21k/49k/49k/9.81M） | 与期望一致（70k/70k/50k/50k/9.83M，同尺寸同 mtime 改写归 identical） | ✅ |
| `_pair_moved` | **1.2 s**（含 100 万重复内容候选对；`_mv_pairs` 临时表 ~20k 命中配对） | 不启用 | oracle 担心的重复内容场景**未成为热点**：join 走 hash 索引、一对一去重流式处理 |
| 幂等复用 | 重跑 **0.0 s**（同 (a,b,hash) 直接复用结果库） | 同左（独立 diff_id `3c8c659d…`） | ✅ |
| 结果库体积 | 122 MiB（190k 行） | ~100 MiB | — |

热点定位：360+ s 几乎全部在 **20M 行对的 Python 归并循环**（逐行 classify + 缓冲写）。`_pair_moved`、CSV 导出、索引都只占零头。
P2 候选优化（未动代码）：把"path 仅一侧存在/两侧内容不同"的筛选用 SQL 完成（UNION ALL + GROUP BY HAVING COUNT(*)≠2，C 层完成 10M 级分组），Python 只对 ~19 万差异行做 classify 与语义判断，预估 3–5×（→ 1.5–2 min）。

## 6. 哈希吞吐（10 万真实小文件，full 策略）

数据：`real100k`（100 目录 × 1000 文件，0–8 KiB 随机，共 0.38 GiB，ext4 页缓存热）。

| 指标 | 实测 |
|---|---|
| 采集（先采集才有快照） | 100,101 条目 / **1.2 s** = **81,486 条目/s** |
| 哈希 full | 100,000 文件 / **4.8 s** = **20,833 文件/s**，读 81.7 MiB/s，RSS 29 MiB |
| 缓存复用 | 重跑 0 计算（"所有文件已有哈希"）；跨快照缓存命中在 P1 已实测 12 万条/次 |

**10M 外推（两段模型：每文件固定开销 + 读带宽）**：
- 纯开销段（小文件，≈48 µs/文件）：10M × 48 µs ≈ **8 min**（即 10M 小文件盘 hash 一遍下限）。
- 带宽段（大文件为主的真实盘）：耗时 ≈ 总字节 ÷ 设备带宽。4 TB 盘 @150 MB/s 顺序读 ≈ **7.5 h**；
  这是设备物理上限，工具侧开销（20.8k 文件/s）在此完全可忽略。
- 结论：按需哈希的规模瓶颈在盘不在工具；对 14 TB 盘的 full 哈希要有"小时级"预期，UI 文案已有分批/续算支撑。

## 7. 真实采集吞吐与 10M 外推

| 场景 | 条目数 | 耗时 | 吞吐 | 说明 |
|---|---|---|---|---|
| `/`（one_filesystem） | 261,112（23.3 万文件 + 1.7 万目录 + 1.1 万软链，跳过 11,485 个跨文件系统挂载点） | **8.7 s** | **28,694 条目/s** | 真实目录树、ext4、页缓存热 |
| real100k | 100,101 | 1.2 s | 81,486 条目/s | 浅层均匀树，缓存极热，偏高估 |

- **外推 3M**：28.7k/s（本环境口径）≈ 1.9 min；外推 10M ≈ 6 min。
- **但这不是真盘口径**：真实冷备场景是 NTFS + 机械盘，冷扫描受寻道支配（每文件至少一次元数据寻道），
  预期只有 1–3k 条目/s 甚至更低，10M 冷扫是**小时级**。工具的批量 stat、帧栈 DFS 在两端差异不大，
  变量主要是盘——所以 P1 验收必须在真盘上做（见 §8）。
- 本环境 `/` 实测文件数 ~23 万（非任务书预估的 81 万），已按实数记录。

## 8. "3M 真盘 ≤ v1 70%" 验收：为何本环境无法验证 + 补验方案

**无法直接验证的原因**：Legacy v1 是 Windows PowerShell 实现（该验收比的是"同一块真盘上 v1 耗时 × 0.7 ≥ 新工具耗时"），
本压测环境是 WSL Linux，既没有 v1 的运行时（PowerShell + .NET 的 NTFS 元数据 API 路径），也没有可比的 NTFS 真盘；
WSL 里通过 /mnt/c 走 9p 协议访问 NTFS，I/O 路径完全失真，两侧数据都不可信。

**补验方案（需用户配合，Windows 侧执行）**：
1. 选同一块真实数据盘（建议 3M 条目量级），Windows PowerShell 跑 Legacy v1 全量采集，记录耗时 T_v1；
2. 同盘用发布包 `cldm collect X:\ --data-root <U 盘/本地目录>` 跑一次，记录耗时 T_v2（注意关掉哈希、首次冷启动后连跑 3 次取后两次均值，排除缓存噪声）；
3. 判定 T_v2 ≤ 0.7 × T_v1；同时比对两侧快照的 file_count / total_bytes / 目录数一致性（可用 `cldm export --format v1_csv` 与 v1 的 tree.csv 做 legacy compare，顺带验证跨代导出）；
4. 把数字回填本报告 §7 的真盘行。

## 9. 达标判定与剩余风险

**判定：10M 规模压测通过（附 1 项超标 + 2 项 P2 建议）**。查询侧全部毫秒级且不随规模衰减；
seal/diff/报告均为分钟级线性放大、内存 O(1)（≤54 MiB）；计数语义经构造数据逐项验证。

| # | 风险 / 待办 | 等级 | 建议 |
|---|---|---|---|
| 1 | stats 聚合 10M 下 6–10 s、RSS 1.58 GiB（temp_store=MEMORY 把 10M 行 GROUP BY 全放内存） | 中（P2 首选） | 快照不可变 → 封库期预计算 ext 分布/深度直方图/零字节计数（同 dir_rollup 模式），请求期直出；顺带消掉 1.5 GiB 内存峰值（低配机风险） |
| 2 | diff 归并循环 18 µs/行对，10M ≈ 6 min | 低（P2） | SQL 下推筛差异行（§4），预估 3–5×；不改变语义 |
| 3 | "3M 真盘 ≤ v1 70%" 未验 | 中（P1 收尾） | 按 §8 方案在 Windows 真盘补验 |
| 4 | 冷机械盘口径缺失（本环境全为热缓存 ext4/NVMe 类） | 中 | 真盘补验时顺带记录冷扫描数字；采集进度条已有,但 10M 冷扫小时级预期要写进用户文档 |
| 5 | FTS 索引 3.31 GiB/10M，库总体积 ≈ 3.2× 原始数据 | 低 | 容量规划口径写入文档（条目数 × 900 B）；`build-fts` 可重建，不需要额外预留一份 |
| 6 | 压测数据集占盘（现存 B1 8.7 GiB + diff 0.12 GiB ≈ 9 GiB） | 低 | B2 可 `scripts/bench10m_make.py` 幂等重造；整套数据可随时删除重生成 |
